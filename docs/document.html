How Shopio AI works with people

The system architecture and the step-by-step flows between the customer, the chat service, ADK, Gemini and support staff, for both approving single actions (tool-level) and handing a whole chat to a person (conversation-level).

Built with Agent Development Kit Cloud Run
Architecture · 2 services

System architecture

Two services, each deployed as its own Cloud Run service. The chat service serves the customer chat, runs the ADK agent and owns all data. The console service serves the staff console, keeps no data of its own, and forwards every action to the chat service's /internal/* API.

  1. The customer sends a message → the chat service runs the agent
  2. The agent calls Gemini and its tools (orders DB)
  3. Events that need a person → streamed to the console over SSE
  4. Staff decide → sent back over HTTP into the same session
Customer sideChat serviceStaff sideMove to a database before scaling

Why ADK lives in the chat service

A person's answer (an approval, accepting a chat) has to go back into the same session the agent is running. The simplest design is for the service that owns the session to receive that answer itself.

Security

  • The console sits behind IAP, so only staff can reach it
  • /internal/* requires INTERNAL_TOKEN and accepts calls from the console service only

Before running several instances

  • ADK sessions → DatabaseSessionService
  • Chats / approvals → Firestore or Cloud SQL
  • SSE across instances → Redis or Pub/Sub
  • Until then, set --max-instances=1
Tool-level · LongRunningFunctionTool

Refunds over 120 baht wait for a supervisor

The agent first looks up the customer's orders and lets them pick one. request_refund is a LongRunningFunctionTool. At or under 120 baht it pays the refund at once. Over 120 it returns pending: no money moves, the customer keeps chatting, and the order shows as In review. When the supervisor approves, the chat service pays the refund and sends the result back to the same function call. Invalid requests (unknown, undelivered, already refunded or already pending) never reach the supervisor.

  1. Gemini calls search_orders; the customer picks an order card
  2. Gemini calls request_refund → returns pending
  3. The customer keeps chatting; the console shows the request
  4. Supervisor approves → the chat service pays it and sends the final result for the same call id

Conversation-level · before_model_callback

Hand the whole chat to a person, then give it back to the AI

The AI is never shut down. human_takeover_guard skips it on every turn while handoff_status is queued or active. When the agent clicks Leave chat, the status goes back to None and the AI replies again.

  1. Gemini calls transfer_to_human → queued
  2. Messages sent while waiting are not sent to Gemini
  3. The agent clicks Accept chat → active
  4. The agent clicks Leave chat → the AI replies again

Session state · handoff_status

Chat states

Every chat is in one of three states. The state is kept in ADK session state, and before_model_callback uses it to decide whether to call Gemini.

  1. ai: Shopio AI replies
  2. queued: the customer asked for a person; waiting for an agent; the AI is silent
  3. active: an agent is chatting; the AI is silent
